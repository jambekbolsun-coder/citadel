# Changelog

## 0.8.1 — 2026-11-04 · деньги и статусы: закрыты обходы правил (этап 1 из docs/SECURITY_FIX_PLAN.md)
- Материал нельзя принять самому себе. Раньше исполнитель мог поставить материал на паузу и из паузы сразу перевести в «сделано», минуя проверку (а принятые материалы идут в сдельную зарплату, соревнования и значки). Теперь с паузы / блокировки исполнитель возвращает материал только в статус, где он был до паузы; руководитель — как раньше. Форма «Следующий шаг» показывает только разрешённый путь.
- Исполнитель больше не может сам назначить себе проверяющего, сдвинуть свой срок или подделать время сдачи — эти поля материала меняются только через назначение и перенос.
- Проект нельзя запустить без 100% оплаты в обход кнопки «Допустить к производству»: прямое изменение статуса и отметки запуска запрещено базой; новый проект — только черновик.
- Оплата при допуске считается в валюте договора: платёж в долларах не закрывает договор в сомах. Суммы в карточке проекта показаны с валютой договора.
- Суммы оплаты проекта видят владелец, финансы, право «видеть цены» / «вносить оплаты», администратор и менеджер проекта. Остальные участники видят только «Оплата: получена полностью / ещё не полностью».
- Статус задачи меняется только кнопками задачи. Закрытую задачу возвращает в работу автор, руководитель или проверяющий (у исполнителя кнопка не показывается).
- Съёмки: «Съёмка проведена» и «Отменить» работают через новые функции базы `shoot_complete` (мобилограф съёмки или руководитель) и `shoot_cancel` (руководитель или директор по планированию, участникам — уведомление). Время, статус и итог съёмки напрямую не правятся.
- Роль или право сотрудника нельзя «переписать» (например, в владельца) — только снять и назначить заново, как и делает экран «Команда».
- Миграция 0024 (только функции, триггеры и уточнение политики; данные не менялись; перед изменением проверено — обходами никто не пользовался). SQL-тест `supabase/tests/rules_hardening.sql` (32 проверки) теперь сам падает при любой ошибке; `content-flow.test.ts`.

## 0.8.0 — 2026-11-04 · значки, серия без просрочек, итоги месяца, дни рождения (этап 3 из docs/GAMIFICATION_PLAN.md)

- Главная: огонёк серии под приветствием илбирса (ссылка на «Мои результаты»).
- Миграция 0023: только новые функции чтения `my_achievements()` (security invoker — свои данные под RLS) и `birthdays_today()`. Задачи «себе самому» в значки не входят. SQL-тест `supabase/tests/achievements.sql` (14 проверок), `achievements.test.ts`.

## 0.7.0 — 2026-11-04 · соревнования сотрудников (этап 2 из docs/GAMIFICATION_PLAN.md)
- Раздел «Соревнования» (`/app/contests`): сезоны, «Мои баллы» с разбивкой, живой рейтинг для владельца, «Зал славы».
- Сезон: даты, участники (все / отделы / роли; владелец не участвует), рейтинг общий или внутри отделов, веса показателей, минимум работ для места, призы 1–2–3 (сумма в сомах и/или текст). Всем сотрудникам — уведомление о новом сезоне.
- Баллы 0–100 из реальных данных (`contest_compute`): план выполнен, вовремя, без правок, сторис по плану, дни в приложении. Задачи «себе самому» не считаются; показатель без данных не снижает баллы; ничьи — по сданным и сданным вовремя.
- До итогов сотрудник видит только свои баллы (`my_contest_score`), рейтинг — только `contests.manage`. «Показать результаты» — после последнего дня сезона: баллы фиксируются в `contest_results`, всем участникам уведомление, при первом открытии — церемония с пьедесталом, празднующим илбирсом и конфетти.
- «Начислить премии» (`payroll.manage`): черновик премии за месяц окончания сезона (в черновик начисления — `bonus_minor`, в утверждённое — корректировка с причиной), один раз на сезон.
- Дни в приложении: одна отметка в день (`app_activity`), без деталей действий.
- Главная: карточка идущего сезона с вашими баллами. Право `contests.manage` (у владельца по умолчанию). Миграция 0022, SQL-тест `supabase/tests/contests.sql` (21 проверка), `contests.test.ts`.

## 0.5.3 — 2026-11-03 · лимит писем: таймер и правила
- Встроенная почта Supabase отправляет не больше 2 писем в час на весь проект (регистрация, повторное письмо, сброс пароля). Свою почту (SMTP) решено не подключать — приложение работает в этом лимите.
- Миграция 0020: журнал отправок `mail_sends` (без email) и функция `email_quota()` — сколько писем ушло за час и когда освободится место (учитывает и время писем в `auth.users`).

- Поле ввода кода убрано: стандартное письмо Supabase содержит только ссылку.

## 0.5.2 — 2026-11-03 · добавление сотрудников без сбоев
- Причина (логи Supabase Auth 03.11): встроенная почта Supabase упёрлась в лимит — 5 регистраций подряд получили 429 `email rate limit exceeded`, аккаунты не создались; форма при этом стирала email и пароль, ошибка была на английском.
- Формы входа, регистрации, приглашения, сброса и смены пароля больше не очищаются при ошибке; ошибки Supabase — по-русски с подсказкой (`src/lib/auth-errors.ts`, тесты).
- После регистрации — экран «Письмо отправлено»: повторная отправка (пауза 60 с), ввод кода из письма (работает на любом устройстве), подсказка про «Спам».
- Повторная регистрация на существующий email больше не делает вид, что письмо ушло: «Аккаунт уже есть — Войти / Забыли пароль?».
- Ссылка из письма, открытая в другом браузере или в приложении Gmail, ведёт на понятный экран «email подтверждён — войдите»; устаревшая ссылка сброса — на запрос новой. Callback поддерживает формат `token_hash` (шаблоны писем `supabase/templates/`).
- На странице приглашения: «Выйти и войти другим email», если вошли не тем аккаунтом. Вход с неподтверждённым email — кнопка «Отправить письмо ещё раз».
- Инструкция по отправке писем через Gmail и русские шаблоны писем: `docs/EMAIL_SETUP.md`.
