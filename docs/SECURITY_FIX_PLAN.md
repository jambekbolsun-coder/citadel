# Исправление пробелов в правилах — согласованный план (04.11.2026)

Основание: полное изучение кода v0.8.0 (коммит `e1e4c6a`). Каждый пункт проверен на боевой базе (политики, триггеры, функции).
Перед планом проверено: пробелами никто не пользовался. 3 проекта запущены через проверку оплаты, материалов 0, задач 2, владелец один. Исправления не затрагивают существующие записи.

## Решения владельца
| Вопрос | Решение |
|---|---|
| Исполнитель снимает материал с паузы / блокировки | Только **обратно в тот статус, где материал был до паузы**. Дальше — обычный путь через проверку. Руководитель — без ограничений, как сейчас |
| Кто видит суммы в карточке «Допуск к производству» | Владелец, финансы (`finance.view`), право видеть цены (`prices.view`), право вносить оплаты (`payments.create`), **а также администратор и менеджер этого проекта**. Остальные видят только «Оплата: есть / нет» |
| Дата рождения | Скрыть от коллег. Видят только сам сотрудник и те, у кого `employees.manage`. Карточка «Сегодня день рождения у …» остаётся |

## Общие правила для всех этапов
- Миграции только добавляющие: новые функции и триггеры, `create or replace`, замена политик. Без DROP таблиц и без перезаписи данных.
- Для каждого пункта — SQL-тест с откатом. С этого плана тесты **сами падают**, если хоть одна проверка `false`: больше не нужно искать `false` глазами в JSON.
- После каждого этапа: typecheck, lint, build, unit-тесты, просмотр экранов в браузере (телефон 375 px, светлая и тёмная тема), обновление docs, коммит, push, проверка деплоя.

## Порядок работ
Вместе с цветными темами (`docs/THEMES_PLAN.md`): **0.8.1** — этап 1 ниже → **0.9.0** — темы → **0.9.1** — этап 2 → **0.9.2** — этап 3.

## Этап 1 — версия 0.8.1: деньги и статусы (важное)
1. **Материал нельзя принять самому себе.**
   - `content_transition`: с паузы / блокировки исполнитель возвращает материал только в статус до паузы (берётся из `content_history`). Руководитель — как раньше.
   - `content_guard` дополнительно защищает поля `reviewer_id`, `submitted_at`, `review_due`, `prep_due`, `publish_due`, `project_id`, `period_id`, `plan_item_id`. Исполнитель больше не может назначить проверяющим себя или сдвинуть свой срок. Сроки переносят только через `content_reschedule`, как и задумано.
   - Почему это важно: принятые материалы идут в сдельную зарплату, в баллы соревнований и в значки.
2. **Статус проекта меняется только через функции.**
   - Новый триггер `projects_guard`: прямое изменение `status`, `launched_at`, `launched_by`, `launch_override_reason` запрещено. Новый проект создаётся только как «черновик».
   - Чек-лист передачи, команда и описание по-прежнему правятся с экрана.
   - Итог: обойти проверку оплаты при запуске больше нельзя.
3. **Проверка оплаты при запуске — в валюте договора.**
   - `project_paid_status` и `launch_project` считают только подтверждённые платежи в валюте договора. Долларовый платёж не закроет договор в сомах.
4. **Статус задачи — только через `task_transition`.**
   - Новый триггер `tasks_guard`: прямое изменение `status`, `completed_at` запрещено. Новая задача создаётся только как «к выполнению».
   - Вернуть в работу сделанную или отменённую задачу может только автор или руководитель.
5. **Съёмки.**
   - Новые функции `shoot_complete` («съёмка проведена» — мобилограф-участник или руководитель) и `shoot_cancel` (отмена с причиной — только руководитель).
   - Триггер `shoots_guard`: статус и время съёмки — только через функции.
   - Мобилограф больше не может напрямую менять проект, время и статус съёмки.
   - Экран съёмки переводится на новые функции, кнопки работают как раньше.
6. **Суммы проекта видят только те, кому положено** (по решению владельца). `project_paid_status` проверяет права: остальным отдаёт только «оплачено полностью / нет». Карточка «Допуск к производству» показывает суммы или только отметку.
7. **Роли нельзя «переписать» в владельца.** Защита ролей и личных прав срабатывает и при изменении записи, а не только при добавлении и удалении. Приложение изменение ролей не использует (только добавление и удаление), поэтому экраны не меняются.

## Этап 2 — версия 0.9.1: утечки и мелкие лазейки
1. Вход: ссылка `/login?next=…` больше не уводит на чужой сайт. Разрешены только адреса внутри приложения.
2. Черновики сайта не видны снаружи: посетителям доступны только опубликованные блоки.
3. Дата рождения скрыта от коллег (по решению владельца). Своя дата — через отдельную функцию на экране профиля. Чтение профиля в `getSession` — явным списком полей вместо `*`.
4. Сторис: исполнитель отмечает факт, но не меняет план и не подтверждает сам себе (`story_daily_plans.planned`, `confirmed_at`).
5. Комментарии и вложения — только к проектам, которые человек видит.
6. Заявки: стадия меняется только через `lead_set_stage` (с причиной для «потерян»).
7. Таймер писем: анонимные отметки отправки ограничены, чтобы чужие запросы не «забивали» таймер. Ещё добавляется кнопка «отправить всё равно» в «Забыли пароль?».
8. Соль адресов в заявках: без переменной `LEAD_IP_SALT` заявки работают как раньше, но в журнал пишется предупреждение (проверить, задана ли переменная в Vercel).

## Этап 3 — версия 0.9.2: правильные цифры на экранах
1. Финансы проекта: суммы с валютой договора. В списке касс при подтверждении оплаты — только кассы той же валюты.
2. Даты «сегодня» по Бишкеку, а не по Лондону: дата оплаты, начало месяца в «Моих результатах», месяц чека, даты проверки рекламы.
3. Большие списки не обрезаются на 1000 строках: суммы касс и рекламы считаются в базе, выгрузки CSV — частями.
4. Календарь: день зарплаты — только по действующим условиям (без дублей после смены оклада).
5. CMS: «вверх / вниз» переставляет только видимые секции.
6. Ежедневные проверки: время выполнения не сбрасывается при повторном сохранении.
7. Журнал `event_outbox` (его никто не читает) больше не пополняется лишними записями. Старые записи не удаляются без отдельного решения владельца.
