# Решения

1. **Один Next.js-проект** для сайта и приложения: `/` публичный, `/app/*` закрыт proxy + RLS.
2. **Права в БД.** Все бизнес-правила — security definer функции с `has_perm`, таблицы под RLS; клиенту доступен только publishable key. Сервисный ключ не используется вовсе.
3. **Первый владелец** назначается через `/setup` + `claim_first_owner` (работает только пока владельца нет). Остальные — только через приглашения.
4. **PIN** проверяется на сервере (bcrypt в `device_pins`, 3 ошибки — пауза 1 мин, 5 — удаление PIN и выход). Это экран блокировки доверенного сеанса, а не способ входа.
5. **Деньги** — bigint в минимальных единицах; суммы вводятся строкой и парсятся без float.
6. **План-факт** вычисляется представлением из plan_items/content_items/placements/story_daily_plans — нет хранимых счётчиков, нет двойного подсчёта.
7. **Тарифы** версионируются; проект хранит `tariff_version_id` и снимок в `project_contracts.tariff_snapshot`. Поправки — `project_amendments` с основанием.
8. **Сторис**: метод фиксируется в проекте (`fixed_per_period` или `four_each_calendar_day`); при 4/день показывается разница с договорным числом.
9. **Секреты** соцсетей — Supabase Vault; просмотр требует входа паролем ≤15 мин (claim `amr` в JWT) и логируется.
10. **Нормативы времени** по умолчанию пустые — система честно пишет «ёмкость не рассчитана».
11. **Web Push**: уведомление пишется в `notifications`, триггер через pg_net будит edge-функцию `push-dispatch` (секрет вызова и ключи VAPID — в Vault, ключи созданы функцией и не покидают сервер). Функция шифрует и отправляет, мёртвые подписки (404/410) удаляет, повторяет до 5 раз, старше суток не шлёт. Входящие + realtime остаются основным каналом.
14. **Серии повторов** разворачиваются в отдельные задачи/съёмки при создании (≤ 60), а не «виртуально»: каждую можно перенести, назначить и закрыть отдельно, план-факт и история работают как обычно. Исполнителю — одно уведомление на серию.
15. **Перетаскивание в календаре** вызывает те же RPC переноса (`task_reschedule`, `shoot_reschedule`, `content_reschedule`) с обязательной причиной — права и история не обходятся.
12. **cacheComponents выключен** — приложение полностью динамическое и персональное, кэширование приватных ответов запрещено (`Cache-Control: private, no-store` для /app, SW не кэширует HTML/API).
13. **Дизайн**: тёмно-зелёная палитра и формы референса kadr-drab (экран входа), красный — только брендинг и акценты. Внутренние экраны референса закрыты авторизацией — точность сравнения ожидает скриншотов от владельца.
18. **Мобильная навигация**: 5 позиций внизу, 4-я — раздел по роли (`resolveWorkTab`), сотрудник может закрепить другой доступный раздел (cookie на устройстве, не в БД). Уведомления — в шапке. Все прочие разделы — из настроек и главной.
19. **Регион функций `dub1`** — рядом с Supabase `eu-west-1`; при `iad1` каждый запрос к БД пересекал Атлантику, страница делает 4–5 последовательных запросов.
20. **Тёмная тема — тёмно-синяя** (референс экрана настроек), светлая — нейтральная; красный — центральная кнопка и главные действия.

21. **Канонический факт рекламы — `campaign_spend_entries`.** Записи не изменяются и не удаляются: исправление создаёт новую запись и помечает старую `superseded_at` с причиной. Распределение общего расхода дня по видео (`p_from_unallocated`) заменяет общую запись разбивкой, итог дня не меняется. `campaign_metrics` — только чтение, её строки перенесены как `legacy`.
22. **План ≠ факт.** Дневной бюджет — плановый лимит с историей (`ad_budget_history`, дата действия, задним числом не меняется). Факт — только журнал расходов, никогда не «бюджет × дни». Активные дни считаются по `ad_status_history`; для кампаний, созданных до 0014, история известна с даты миграции (`history_from`).
23. **Валюты раздельно, без автоконвертации.** Курс не придумывается: суммы показываются по каждой валюте. Движение по кассе принимается только в валюте кассы (триггер `money_tx_currency_guard`), платёж — в валюте счёта. Если понадобится эквивалент — отдельная таблица курсов с датой и автором.
24. **Права таргетолога — по проекту.** Видимость кампаний: свой `owner_id`, участие в проекте (с `campaigns.manage`), управление проектом или `campaigns.view_all`. Клиента проекта видит таргетолог проекта (`is_ad_member`). Пароли соцсетей — по-прежнему отдельное право `credentials.reveal` и только на видимых проектах; создание/удаление доступа теперь тоже проверяет проект.
25. **Утверждение сотрудника — только RPC** `employee_set_status`; прямой UPDATE статуса из приложения больше не используется. Повторное нажатие ничего не меняет.
26. **Неполный месяц зарплаты** начисляется по договорному правилу из условий (оклад целиком), без автоматического пропорционального расчёта — как требует ТЗ; изменение правила — решение владельца.
27. **Инструкции — типизированный контент в Git** (`src/lib/help-content.ts`), без секретов; локализация KG — отдельным объектом с теми же id.

28. **Бренд без переименования инфраструктуры.** Пользователю видно только «SMM KADR»; ключи `citadel.*` (localStorage, cookie, настройка `citadel.bypass`), имя репозитория и проекта Vercel, адрес `citadel-tawny.vercel.app` не меняются, чтобы не терять сессии, PIN-устройства и историю. `manifest.id = /app` сохранён — установленное приложение обновляется, а не ставится заново.
29. **Логотип — вектор по оригиналу.** Знак восстановлен по маске логотипа из PDF (два многоугольника), надпись — контуры Montserrat ExtraBold, поэтому PNG любого размера генерируются скриптом без потери чёткости. Иконка приложения — только знак (название в 48 px не читается).
30. **Клиент и проект — одна транзакция в БД** (`project_wizard_create`), а не цепочка запросов из Next: нет состояния «клиент создан, проект нет»; идемпотентность через уникальный ключ проекта и advisory lock.
31. **Дубли клиентов — по последним 9 цифрам телефона** (`phone_key`, вычисляемая колонка). При совпадении сервер не создаёт клиента и предлагает существующего; второго с тем же номером можно создать только явным подтверждением. Профиль существующего клиента меняется из мастера только флажком «Уточнить данные» и с правом `clients.manage`.
32. **Оплата в мастере — заявленная, не подтверждённая.** «Клиент дал 15 000» становится платежом `pending` (+ счёт на предоплату и счёт на остаток); в кассу и «оплачено» сумма попадает только после `payment_confirm`. Создание проекта не допускает его к производству.
33. **Сайт = секции-слайды одной схемы** (`site_blocks.type = 'slide'`): любая из 15 страниц собирается из необязательных полей (рубрика, плашка, заголовок, цена, цифры, список, команда, карточка, сноска, изображения, кнопки). Один редактор на все секции; только текст, без HTML; изображения только из `/site/…` или bucket `site`.
34. **Цена на сайте и цена в договоре — разные сущности.** Сайт показывает маркетинговый текст (или текущую версию тарифа, если поле пустое); мастер и договоры используют справочник тарифов со снимком версии. Расхождение подсвечивается в CMS; публичная цена не меняет действующие договоры.
